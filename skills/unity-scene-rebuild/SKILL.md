# Unity Scene Rebuild

For projects whose scene is **procedurally generated by a project-owned menu item** (e.g. `States At War/Setup Scene 3D`). That generator is the source of truth for scene layout; the `.unity` file in version control is only a snapshot of a correct run. After any structural code change — a new component on an anchor object, a renamed type the generator instantiates, a changed prefab wiring — re-run the generator and **verify the output** before calling the task done.

**Lane.** This skill runs an *authoritative generator that already exists*. If there is no project generator and you need to build a scene from scratch with `manage_scene` / `manage_gameobject`, that is `unity-scene-setup`, not this. For the base orient→act→verify loop, safety-mode mechanics, and refusal handling, this skill assumes `unity-mcp-operator`. To fix compile errors before rebuilding, hand off to `unity-edit-verify`.

## Posture — this needs `write` mode AND an allowlisted menu path

The generator runs through `execute_menu_item`, which is **DESTRUCTIVE-class** (it invokes arbitrary Editor code) and **allowlist-gated**. Two independent gates must both pass:

1. **Safety mode.** `execute_menu_item` and `manage_scene(action="save")` need `write` mode. Check first:

   ```python
   safety_status()   # mode must be "write"; note menu_item_allowlist
   ```

   In `read_only` / `review_only`, stop and report: the rebuild cannot run in this mode, no changes were made. Do not attempt a workaround.

2. **Menu allowlist.** The generator's menu path must be on the `execute_menu_item` allowlist. The default allowlist contains only window-opening items (Console, Hierarchy, Inspector, …) — a **project generator is NOT on it by default**. The operator must add it out-of-band:

   ```
   UNITY_MCP_MENU_ITEM_ALLOWLIST="States At War/Setup Scene 3D"
   ```

   `safety_status().menu_item_allowlist` lists the currently permitted paths. If the path is absent, expect Step 2's call to be refused; handle that refusal (see Step 2) rather than retrying.

`confirm:true` on the generator call is destructive-operation acknowledgement metadata — it does not relax the mode and is not a human sign-off. It is required in `write` mode for the DESTRUCTIVE call to proceed; it is never sufficient on its own.

## Step 0 — Orient and confirm the scene is safe to rebuild

Running the generator over a dirty scene silently destroys unsaved manual edits, and creating/loading scenes has no `confirm` gate. Before anything:

1. One read for situational awareness: `mcpforunity://editor/context` (unions editor state + selection + prefab-stage + console counts).
2. Read the active scene's dirty flag — the action is `get_active`, not `status`:

   ```python
   manage_scene(action="get_active")   # → data.isDirty, data.name, data.path
   ```

   For multi-scene setups, `manage_scene(action="get_loaded_scenes")` reports `isDirty` per scene.
3. **If dirty:** stop. Report the dirty scene(s) and ask whether to (a) discard unsaved edits and rebuild, (b) snapshot first, then rebuild, or (c) abort. Do not silently overwrite.
4. **Snapshot before the rebuild** (recommended, and mandatory for choice (b)) so you can roll back:

   ```python
   manage_checkpoint(action="create", label="pre-rebuild")   # VALIDATE
   ```

   This copies each loaded, saved scene under `Library/McpCheckpoints/<id>/`. See "Rollback" below for restore semantics.

A clean baseline makes the rebuild reproducible and the version-controlled `.unity` diff meaningful.

## Step 1 — Confirm compile state

The generator instantiates your types; running it over a broken build produces a corrupt or partial scene.

```python
read_console(action="get", types=["error", "warning"], format="summary")
```

`format="summary"` collapses duplicate signatures to counts. If any **error** signatures exist, stop and resolve them with `unity-edit-verify` first. Also confirm the editor is idle — read `mcpforunity://editor/state` and require `compilation.is_compiling == false` and `advice.ready_for_tools == true` before proceeding.

Record the warning count now; it is the baseline Step 5 compares against.

## Step 2 — Run the generator and wait for completion

```python
execute_menu_item(menu_path="States At War/Setup Scene 3D", confirm=true)
```

The exact path must match the `[MenuItem(...)]` attribute on the generator (here `States At War/Assets/Editor/SceneSetup3D.cs`) **and** the allowlist entry, character for character.

**If the call is refused**, read the refusal text and act on which gate tripped — do not retry verbatim:
- "not on the execute_menu_item allowlist" → the path needs `UNITY_MCP_MENU_ITEM_ALLOWLIST`. Report that to the user; you cannot self-authorize it.
- "blocks this call … classified as 'destructive'" → the server is not in `write` mode. Report the mode; no changes were made.

**Completion is not the return.** `execute_menu_item` may return as soon as the item is invoked, before the generation (or a triggered domain reload) finishes:

1. Poll `mcpforunity://editor/state` until `compilation.is_compiling == false` and `advice.ready_for_tools == true`. A heavy generator can trigger a domain reload — wait for it to complete.
2. Then `read_console(action="get", types=["error"], count=20)`. A generator exception is logged here — investigate before Step 3.
3. If the call returned an explicit success/failure structure, treat that as the primary signal and the console as corroboration.

Do not proceed while the editor reports busy.

## Step 3 — Verify anchors, counts, and components

Existence is not enough — count matters, because a generator that fails to clear prior state leaves orphans alongside the fresh objects. Use `query_scene` (READ): one call filters by component type and projects the components, giving you count **and** wiring without a find→get-components loop.

```python
# Camera anchor: expect exactly one, carrying both components.
query_scene(component_type="RTSCamera", include=["components"])
# → { total_matched, rows: [ { name, path, components: [...] } ] }
```

Read `total_matched` for the count and each row's `components` for the expected set:

| Anchor (by component) | Expected components | Expected `total_matched` |
|---|---|---|
| `RTSCamera` | `Camera`, `RTSCamera` | 1 |
| `Light` (Directional) | `Light` | 1 |
| `GameManager` | `GameManager`, `AIController`, `SelectionHandler`, `FogOfWarController` | 1 |

Decision rules:
- **`total_matched == 0`** for a required anchor → generation failed or threw partway. Re-check `read_console(types=["error"])` for the failure point before continuing.
- **`total_matched > 1`** → the generator did not clear prior state. Surface this as a finding: duplicates exist and must be resolved (by the user, or by fixing the generator to `DestroyImmediate` existing instances before generating). Do not treat it as success.
- **A row missing an expected component** → the generator did not wire that component; report the object and the missing type.

**Bulk count spot-check.** For the repeated objects (e.g. 28 provinces), read the count directly:

```python
query_scene(name_contains="Province", page_size=1)   # → total_matched is the count
```

Use `component_type=` instead if the objects share a marker component but not a name prefix. Report the actual `total_matched` against the expected count; a mismatch means a generation failure mid-loop — investigate, do not ignore.

(`find_gameobjects` also exists but returns **instance IDs only** — no components, and it has no `name_pattern` parameter. Prefer `query_scene` here; it answers count and wiring in one call.)

## Step 4 — Save the scene

```python
manage_scene(action="save")   # WRITE
```

Then confirm the write landed — do not assume it:

```python
manage_scene(action="get_active")   # data.isDirty must be false
```

A scene still reporting `isDirty == true` after `save` means the save did not take; report it as a failure, not a success.

## Step 5 — Console check against baseline

```python
read_console(action="get", types=["error", "warning"], format="summary")
```

Compare against the Step 1 baseline. Do **not** `read_console(action="clear")` — clearing is a WRITE and destroys the evidence you are reporting on.

Blocking (fix before claiming done):
- New `MissingReferenceException` / `NullReferenceException` signatures traced to the generation.
- Missing serialized-field warnings on freshly created objects (a property the generator failed to wire), unless the field is genuinely optional.
- Any error naming a type you just changed that the generator instantiates.

Non-blocking but report: new scene-file warnings (orphaned components, missing scripts), and any pre-existing warning the rebuild re-introduced after it was previously fixed.

## Rollback

If verification fails and you snapshotted in Step 0, roll back:

```python
manage_checkpoint(action="restore", id="pre-rebuild", confirm=true)
```

`restore` is **DESTRUCTIVE**: it overwrites the original scene files on disk with the snapshot and discards current unsaved scene changes (refused in play mode or while compiling). `confirm:true` acknowledges that; it does not soften it. Needs `write` mode. `manage_checkpoint(action="list")` (READ) shows available ids.

## Step 6 — Report only what you observed

State plainly, citing the numbers you actually read:
- **Trigger** — the structural change that prompted the rebuild.
- **Pre-rebuild state** — dirty/clean (Step 0); console baseline errors/warnings (Step 1); whether a checkpoint was created.
- **Per-anchor result** — `total_matched` and the observed component set for each row in the Step 3 table.
- **Bulk count** — actual `total_matched` vs expected.
- **Save** — confirmed (`isDirty == false`) or failed.
- **Console** — "no new errors or warnings vs baseline" or the list of new signatures with blocking/non-blocking status.

Never write "scene rebuilt" without the Step 3 counts and the Step 4 `isDirty == false` confirmation behind it. If a step was skipped because the mode or allowlist forbade it, say "skipped (write mode required)" or "skipped (menu path not allowlisted)" — never imply it succeeded.

## Optional — boot verdict after the rebuild

A verified scene still may not play. If asked to confirm the game boots, hand off to `unity-test-pilot` (`play_smoke_test`) — that path is VALIDATE-class and lives in the `testing` tool group, which is disabled by default; it is out of this skill's lane.
